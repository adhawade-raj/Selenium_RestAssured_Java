# API Automation Framework — Theory & Architecture

## Framework Overview

We have designed our API automation framework using **Java, Rest Assured, and TestNG**. The framework follows a **layered architecture** to keep responsibilities clear and tests maintainable. This is a pure API-centric testing framework with no BDD dependencies (Cucumber is optional).

---

## Layered Architecture

```
┌─────────────────────────────────────────┐
│      TestNG Test Classes                │  ← @Test methods in test layer
├─────────────────────────────────────────┤
│          BaseTest & Fixtures            │  ← @BeforeTest, @BeforeMethod, @AfterTest
├─────────────────────────────────────────┤
│   Authentication & Token Management    │  ← Token refresh, expiry handling
├─────────────────────────────────────────┤
│  RestClient (GET/POST/PUT/PATCH/DELETE)│  ← Request execution layer
├─────────────────────────────────────────┤
│   Configuration Manager & Properties   │  ← Env-specific config, URLs, credentials
├─────────────────────────────────────────┤
│    Utilities, Constants & Enums        │  ← Reusable logic & shared resources
└─────────────────────────────────────────┘
```

## Core Components & Responsibilities

### 1. Configuration Manager
**Purpose**: Centralize environment-specific settings

**Responsibilities**:
- Reads environment-specific configuration (API base URLs, credentials, timeouts)
- Loads properties from files (e.g., `dev.config.properties`, `qa.config.properties`, `stage.config.properties`)
- Manages environment selection
- Exposes configuration to RestClient and test layers

**Key Concept**: Avoid hardcoding URLs, tokens, or credentials. All configuration is externalized.

---

### 2. RestClient Layer (Common HTTP Layer)
**Purpose**: Encapsulate Rest Assured request execution for all HTTP methods

**Responsibilities**:
- Encapsulates Rest Assured calls for **GET, POST, PUT, PATCH, DELETE**
- Builds `RequestSpecification` with headers, authentication, content-type, query parameters
- Handles request/response logging
- Provides methods returning deserialized POJOs or raw `Response` objects
- Manages authorization headers and token injection

**Key Methods**:
- `get(endpoint, queryParams, headers, includeAuth, log)` — Retrieve data
- `post(endpoint, contentType, requestBody, headers, includeAuth, log)` — Create resources
- `put(endpoint, contentType, requestBody, headers, includeAuth, log)` — Full update
- `patch(endpoint, contentType, requestBody, headers, includeAuth, log)` — Partial update
- `delete(endpoint, headers, includeAuth, log)` — Remove resources

**Design Pattern**: All HTTP operations go through RestClient; tests never call Rest Assured directly.

---

### 3. Authentication & Prerequisite Layer
**Purpose**: Manage API authentication and token lifecycle

**Responsibilities**:
- Invokes authentication APIs when required
- Retrieves and caches access tokens
- Injects tokens into subsequent requests via authorization headers
- Handles token expiry and refresh logic
- Manages prerequisite data creation (test setup data)

**Token Handling Flow**:
```
Test Execution
    ↓
Check Token Validity
    ↓
[Expired?] → Refresh Token → Store New Token
    ↓
Execute Test with Valid Token
    ↓
[Cleanup?] → Delete Prerequisite Data
```

**Key Pattern**: Tokens are centralized and reused across tests to avoid repeated authentication calls.

---

### 4. BaseTest Class
**Purpose**: Manage common test setup and teardown

**Responsibilities**:
- Initialize RestClient instances with properties
- Set up common headers and authentication via `@BeforeTest`, `@BeforeMethod`
- Configure Allure reporting filters (e.g., `RestAssured.filters(new AllureRestAssured())`)
- Handle test preconditions (load config, prepare tokens)
- Handle test postconditions via `@AfterTest`, `@AfterMethod`
- Expose service endpoint URLs as constants (e.g., `GOREST_ENDPOINT = "/public/v2/users"`)

**TestNG Annotations**:
- `@Parameters` — Receive parameters from TestNG XML
- `@BeforeTest` — Execute once before all test methods in class
- `@BeforeMethod` — Execute before each test method
- `@AfterMethod` — Execute after each test method
- `@AfterTest` — Execute once after all test methods in class

---

### 5. Test Layer
**Purpose**: Contain actual test methods using TestNG annotations

**Test Characteristics**:
- TestNG test methods using `@Test` annotation
- Support for `@Parameters` to receive parametrized values from TestNG XML
- Support for `@DataProvider` to supply test data programmatically
- `@BeforeMethod` and `@BeforeMethod` for setup/teardown
- Focused on single API endpoint or workflow
- Use RestClient for all API calls
- Assert response status, body, headers using Hamcrest matchers or assertions
- Capture logs automatically via Allure reporting

**Test Structure (AAA Pattern)**:
```java
@Test
public void testGetUserById() {
    // Arrange - Prepare test data
    int userId = 123;
    
    // Act - Call REST API
    Response response = restClient.get("/users/" + userId, true, true);
    
    // Assert - Verify response
    response.then().assertThat().statusCode(200);
}
```

---

### 6. Payloads & POJO Mapping
**Purpose**: Model request and response payloads

**Technologies**:
- **Lombok** — Reduces boilerplate code for POJOs (getters, setters, constructors, equals, hashCode, toString)
- **Jackson Databind** — Serializes Java objects to JSON and deserializes JSON to POJOs

**Pattern**:
```java
@Data  // Lombok annotation (generates getters, setters, equals, hashCode, toString)
@AllArgsConstructor
@NoArgsConstructor
public class User {
    private String name;
    private String email;
    private String phone;
}

// Usage in RestClient:
User user = response.as(User.class);  // Automatic deserialization via Jackson
```

**Key Benefit**: Minimizes code bloat and keeps POJOs clean and readable.

---

### 7. Data-Driven Testing
**Purpose**: Enable multiple test scenarios with different inputs

**Mechanisms**:
- **Excel Utility** — Read test data from `.xlsx` files
- **TestNG DataProvider** — Supply multiple test cases programmatically
- **TestNG Parameters** — Pass parameters from XML configuration

**Pattern** (Excel-driven):
```java
@DataProvider(name = "userTestData")
public Object[][] getUserTestData() {
    List<Map<String, String>> data = ExcelUtility.readTestData(
        "src/test/resources/testdata.xlsx", 
        "Users"
    );
    // Convert to Object[][] for TestNG
}

@Test(dataProvider = "userTestData")
public void testCreateUser(Map<String, String> testData) {
    String name = testData.get("Name");
    String email = testData.get("Email");
    // Execute test with different data
}
```

**Benefit**: Single test method can run multiple times with different inputs, reducing code duplication.

---

### 8. Utilities, Constants & Enums
**Purpose**: Provide reusable helpers and domain concepts

**Common Utilities**:
- **ExcelUtility** — Read/write Excel files for data-driven testing
- **JsonPathValidator** — Extract and validate JSON path expressions
- **XmlPathValidator** — Extract and validate XML path expressions
- **StringUtils** — Common string operations
- **RandomDataGenerator** — Generate random test data (emails, phone numbers, etc.)

**Common Enums**:
- **APIHttpStatus** — HTTP status codes (OK_200, CREATED_201, BAD_REQUEST_400, UNAUTHORIZED_401, etc.)
- **APIConstants** — Endpoint URLs, timeouts, retry counts

**Key Benefit**: Reusable code lives in one place; changes propagate to all tests.

---

### 9. Reporting & Artifacts
**Purpose**: Generate comprehensive test execution reports

**Technology**: **Allure** (allure-testng, allure-rest-assured)

**Capabilities**:
- Captures all test steps and their outcomes
- Logs request/response bodies and headers automatically (via `RestAssured.filters(new AllureRestAssured())`)
- Supports custom steps via `@Step` annotation
- Generates interactive HTML reports with charts, timelines, and failure analysis
- Stores raw test data in `allure-results/` directory

**Allure Annotations**:
```java
@Feature("User Management")
@Story("User CRUD Operations")
public class UserAPITest extends BaseTest {
    
    @Test
    @Description("Create a new user with valid credentials")
    @Severity(SeverityLevel.CRITICAL)
    public void testCreateUserSuccessfully() {
        // Test code
    }
    
    @Step("Creating user with email: {email}")
    private void createUser(String email) {
        // Step implementation
    }
}
```

## Design Principles

### 1. **Reusability**
- Common utilities, constants, and enums are shared across all layers
- RestClient methods are reused in multiple tests
- BaseTest provides common setup/teardown logic

### 2. **Readability**
- Clear separation of concerns; each layer has a single responsibility
- Test methods read like plain English (clear test names, AAA pattern)
- Configuration is centralized and easy to find

### 3. **Maintainability**
- Centralized configuration; changing a URL or credential updates all tests
- Minimal code duplication via reusable helpers
- Changes to RestClient automatically propagate to all tests

### 4. **Scalability**
- Pure API-centric design scales to thousands of tests
- Layered architecture supports future extensions (UI testing, performance testing, etc.)
- DataProvider and Excel utilities support data-driven expansion

### 5. **Reliability**
- Token refresh logic handles auth failures gracefully
- Retry logic for transient failures
- Comprehensive logging for debugging failed tests
- Error handling and validation at each layer

## Test Execution Flow (Typical Sequence)

```
1. Maven Project Build
   └─ Load pom.xml dependencies (RestAssured, TestNG, Allure, Jackson, Lombok, etc.)

2. TestNG Test Discovery
   └─ Scan for test classes
   └─ Parse TestNG XML configuration (testng.xml)
   └─ Load parameters (baseURI, environment, etc.)

3. BaseTest @BeforeTest
   └─ Initialize ConfigurationManager
   └─ Load Properties from config files (dev.config.properties, etc.)
   └─ Add Allure filter to RestAssured (RestAssured.filters(new AllureRestAssured()))

4. For Each Test Method:
   
   a. @BeforeMethod
      └─ Initialize RestClient with properties and baseURI
      └─ Perform Authentication (if required)
      └─ Store access token for subsequent requests
   
   b. @Test Execution
      ├─ Prepare test data (inline or from @DataProvider)
      ├─ Call RestClient method (GET/POST/PUT/PATCH/DELETE)
      ├─ Receive Response object
      ├─ Assert status code, headers, body
      ├─ Extract data from response (jsonPath, as(POJO.class))
      └─ Logs captured automatically by Allure filter
   
   c. @AfterMethod
      └─ Delete test data (cleanup prerequisites)
      └─ Close connections if needed

5. BaseTest @AfterTest
   └─ Global cleanup if required
   └─ Close configuration resources

6. Report Generation
   └─ Allure processes test results and logs from allure-results/
   └─ Generate interactive HTML report via `mvn allure:report`
   └─ View report via `mvn allure:serve`
```

## Configuration Management Pattern

**Config Files Location**: `src/test/resources/config/`

**Example Properties File** (dev.config.properties):
```properties
# API Configuration
api.base.url=https://gorest.co.in
api.timeout=5000
api.retry.count=3

# Authentication
tokenId=your-bearer-token-here
auth.endpoint=/v1/security/oauth2/token

# Headers
api.content.type=application/json
api.accept.type=application/json

# Environment
env=dev
log.level=INFO
report.path=./allure-results
```

**Usage in Code**:
```java
public class ConfigurationManager {
    public Properties initProp() {
        Properties prop = new Properties();
        String configPath = "src/test/resources/config/dev.config.properties";
        try (InputStream input = new FileInputStream(configPath)) {
            prop.load(input);
        } catch (IOException e) {
            throw new APIFrameworkException("Config file not found");
        }
        return prop;
    }
}

// In BaseTest:
config = new ConfigurationManager();
prop = config.initProp();
String baseURI = prop.getProperty("api.base.url");
```

## Summary

This layered architecture with TestNG provides a solid foundation for scalable, maintainable API automation. By centralizing configuration, abstracting HTTP operations through RestClient, and using TestNG's built-in features (DataProvider, Parameters, Annotations), the framework minimizes boilerplate and maximizes reusability. Each layer has a clear responsibility, making the codebase easy to understand and extend.
