# BDD Cucumber Style Selenium Framework with BrowserStack

Interview-ready notes on Cucumber BDD automation framework combining local and cloud-based (BrowserStack) execution.

The framework evolves from traditional TestNG/BaseTest architecture to Cucumber-driven BDD approach. The core driver logic is centralized through StartDriver, which routes execution to either LocalDriver (for local browsers) or BSDriverHelper (for BrowserStack cloud execution) based on runtime parameters.

---

## 1. Framework Overview

The framework is a hybrid Java UI automation framework combining Cucumber BDD, Page Object Model (POM), layered architecture, reusable utilities, centralized configuration, data-driven testing, reporting/logging and CI/CD integration.

- **Language:** Java
- **UI Automation:** Selenium WebDriver
- **BDD Framework:** Cucumber
- **Design Approach:** Hybrid framework + POM + Layered/DDD-style organization
- **Test Execution:** Cucumber Runner with JUnit/TestNG integration
- **Build/Dependency Management:** Maven
- **Configuration:** Properties files with environment/browser values
- **Test Data:** Excel/XLSX
- **Local Execution:** Chrome / Firefox / Edge using local Selenium drivers
- **Cloud Execution:** BrowserStack using RemoteWebDriver
- **CI/CD:** Jenkins
- **Source/Artifact Ecosystem:** Git + Nexus
- **Reporting/Logging:** Cucumber / Extent / Allure-style reports, logs, screenshots

**Architecture Evolution:** The original framework used TestNG/BaseTest and a DriverFactory. The revised architecture uses Cucumber feature files and Hooks for scenario lifecycle, with a centralized StartDriver that selects either LocalDriver or BSDriverHelper based on runtime arguments.

---

## 2. High-Level Architecture Flow

The framework follows a layered architecture with clear separation of concerns from test execution through to reporting and infrastructure.

```
Cucumber Runner (@RunWith, @CucumberOptions)
    ↓
Feature Files (Given / When / Then)
    ↓
Cucumber Hooks (@Before / @After)
    ↓
StartDriver (platform + browser routing)
    ↓
    ├─→ LocalDriver (Chrome / Firefox / Edge)
    │   ↓
    │   Local WebDriver instances
    │
    └─→ BSDriverHelper
        ↓
        BrowserStack RemoteWebDriver
    ↓
Step Definitions (maps Gherkin to Java)
    ↓
Page Objects (UI element actions)
    ↓
Selenium Actions & Validation
    ↓
@After Hook (screenshot on failure, cleanup)
    ↓
Reports & Screenshots
```

**Key Design Principle:** Driver-selection logic is centralized in StartDriver. Step Definitions and Page Objects do not need to know whether execution is local or BrowserStack.

## 3. Layer-by-Layer Explanation

| Layer | What it Contains | Responsibility | Interview Explanation |
|-------|---|---|---|
| **Feature Layer** | `.feature` files with Gherkin syntax | Business-readable scenarios | Defines test behavior in Given/When/Then format without technical details. |
| **Step Definition Layer** | `*StepDefinition.java` classes | Maps Gherkin steps to Java methods | Bridges Gherkin and Page Objects. Should remain thin: receive data, call Page Object methods, assert results. |
| **Hooks Layer** | `Hooks.java` with @Before/@After | Scenario setup/teardown, lifecycle management | Replaces BaseTest. Initializes driver before each scenario, captures screenshots on failure, quits driver after. |
| **StartDriver** | `StartDriver.java` | Central driver entry point | Reads platform/browser system properties and routes to LocalDriver or BSDriverHelper. Uses ThreadLocal for parallel execution. |
| **LocalDriver** | `LocalDriver.java` | Local browser instantiation | Creates ChromeDriver, FirefoxDriver, EdgeDriver with appropriate options. |
| **BSDriverHelper** | `BSDriverHelper.java` | BrowserStack RemoteWebDriver creation | Initializes RemoteWebDriver with BrowserStack capabilities, OS/browser selection, and credentials. |
| **Page Layer** | `BasePage.java`, `LoginPage.java`, etc. | UI element locators and page-specific actions | Encapsulates locators and Selenium actions so tests do not directly contain XPath/sendKeys/etc. |
| **Configuration Layer** | `ConfigurationManager.java`, `*.properties` | Environment-specific values | Externalizes URL, waits, environment and runtime flags. Avoids hardcoding. |
| **Utility Layer** | `WaitUtility.java`, `ExcelUtility.java`, etc. | Reusable support functions | Provides explicit waits, Excel/data reading, JavaScript execution, screenshots, constants. |
| **Runner Layer** | `TestRunner.java` with @CucumberOptions | Cucumber execution configuration | Defines features path, glue code packages, tags, plugins and report configuration. |
| **CI/CD** | Jenkins jobs/pipeline | Automation trigger and parameter passing | Triggers Maven builds, passes runtime arguments (platform, browser, environment), publishes results. |
| **Execution Infrastructure** | Local machine / BrowserStack cloud | Browser and environment execution | Supports local browser execution and cloud-based cross-browser testing. |
| **Repository / Artifacts** | Git + Nexus | Source and build artifact management | Git manages source code; Nexus manages build artifacts. |

## 3.1 Code Examples

### 1. StartDriver — Central Driver Entry Point

StartDriver reads runtime arguments and decides which implementation should create the WebDriver. It uses ThreadLocal to support parallel execution by keeping a separate WebDriver instance per thread.

```java
public class StartDriver {
    
    private static ThreadLocal<WebDriver> driver = new ThreadLocal<>();
    
    public static void initializeDriver() {
        String platform = System.getProperty("platform", "local");
        String browser = System.getProperty("browser", "Chrome");
        
        WebDriver webDriver;
        
        if (platform.equalsIgnoreCase("browserstack")) {
            webDriver = BSDriverHelper.createDriver(browser);
        } else {
            webDriver = LocalDriver.createDriver(browser);
        }
        
        driver.set(webDriver);
    }
    
    public static WebDriver getDriver() {
        return driver.get();
    }
    
    public static void quitDriver() {
        if (driver.get() != null) {
            driver.get().quit();
            driver.remove();
        }
    }
}
```

**Key Point:** Using `ThreadLocal<WebDriver>` prepares the framework for parallel execution by keeping a separate WebDriver instance per execution thread.

### 2. LocalDriver — Local Browser Initialization

LocalDriver is responsible only for local Selenium browser creation. It keeps local browser-specific setup separate from BrowserStack logic.

```java
public class LocalDriver {
    
    public static WebDriver createDriver(String browser) {
        WebDriver driver = null;
        
        switch (browser.toLowerCase()) {
            case "chrome":
                ChromeOptions chromeOptions = new ChromeOptions();
                chromeOptions.addArguments("--start-maximized");
                chromeOptions.addArguments("--disable-notifications");
                driver = new ChromeDriver(chromeOptions);
                break;
                
            case "firefox":
                FirefoxOptions firefoxOptions = new FirefoxOptions();
                firefoxOptions.addArguments("--start-maximized");
                driver = new FirefoxDriver(firefoxOptions);
                break;
                
            case "edge":
                EdgeOptions edgeOptions = new EdgeOptions();
                edgeOptions.addArguments("--start-maximized");
                driver = new EdgeDriver(edgeOptions);
                break;
                
            default:
                throw new IllegalArgumentException("Unsupported browser: " + browser);
        }
        
        return driver;
    }
}
```

### 3. BSDriverHelper — BrowserStack RemoteWebDriver Initialization

BSDriverHelper is responsible for BrowserStack-specific RemoteWebDriver initialization and capabilities. The framework can support cross-browser testing without changing feature files or Step Definitions.

```java
public class BSDriverHelper {
    
    public static WebDriver createDriver(String browser) {
        try {
            MutableCapabilities capabilities = new MutableCapabilities();
            capabilities.setCapability("browserName", browser);
            
            Map<String, Object> bstackOptions = new HashMap<>();
            bstackOptions.put("os", "Windows");
            bstackOptions.put("osVersion", "11");
            bstackOptions.put("buildName", "Automation Framework Build");
            bstackOptions.put("sessionName", "Cucumber Test");
            
            capabilities.setCapability("bstack:options", bstackOptions);
            
            String username = System.getenv("BROWSERSTACK_USERNAME");
            String accessKey = System.getenv("BROWSERSTACK_ACCESS_KEY");
            String hubUrl = "https://" + username + ":" + accessKey + 
                          "@hub-cloud.browserstack.com/wd/hub";
            
            return new RemoteWebDriver(new URL(hubUrl), capabilities);
            
        } catch (Exception e) {
            throw new RuntimeException("BrowserStack driver initialization failed", e);
        }
    }
}
```

**Security Note:** BrowserStack credentials should be supplied through Jenkins credentials or environment variables. Do not hardcode access keys in source code.

### 4. Hooks — Scenario Lifecycle Management

The original framework used BaseTest for common setup/teardown. In the Cucumber version, scenario lifecycle is handled by Cucumber Hooks. This makes the lifecycle naturally scenario-oriented and replaces @BeforeTest/@AfterTest responsibilities.

```java
public class Hooks {
    
    @Before
    public void setUp(Scenario scenario) {
        System.out.println("Starting scenario: " + scenario.getName());
        
        StartDriver.initializeDriver();
        StartDriver.getDriver().manage().window().maximize();
        
        StartDriver.getDriver().manage().timeouts().implicitlyWait(
            Duration.ofSeconds(
                ConfigurationManager.getInstance().getImplicitWait()
            )
        );
        
        StartDriver.getDriver().manage().timeouts().pageLoadTimeout(
            Duration.ofSeconds(
                ConfigurationManager.getInstance().getPageLoadTimeout()
            )
        );
    }
    
    @After
    public void tearDown(Scenario scenario) {
        if (scenario.isFailed()) {
            captureScreenshot(scenario);
        }
        
        StartDriver.quitDriver();
    }
    
    private void captureScreenshot(Scenario scenario) {
        byte[] screenshot = ((TakesScreenshot) StartDriver.getDriver())
            .getScreenshotAs(OutputType.BYTES);
        scenario.attach(screenshot, "image/png", scenario.getName());
    }
}
```

**Mapping from Old Framework:**
- `@BeforeTest / @BeforeMethod` → `@Before`
- `@AfterMethod / @AfterTest` → `@After`

### 5. ConfigurationManager — Environment & Configuration Management

Configuration remains externalized. Environment-specific values (URL, waits) stay outside test code. Runtime execution values (platform, browser) are supplied through Java system properties.

```java
public class ConfigurationManager {
    
    private Properties prop;
    private static ConfigurationManager configManager;
    
    private ConfigurationManager() {
        prop = new Properties();
        String propFile = "application-" + getEnvironment() + ".properties";
        
        try (InputStream input = getClass().getClassLoader()
                .getResourceAsStream(propFile)) {
            if (input != null) {
                prop.load(input);
            }
        } catch (IOException e) {
            System.out.println("Unable to load properties file: " + e.getMessage());
        }
    }
    
    public static ConfigurationManager getInstance() {
        if (configManager == null) {
            configManager = new ConfigurationManager();
        }
        return configManager;
    }
    
    public String getEnvironment() {
        return System.getProperty("env", "qa");
    }
    
    public String getApplicationUrl() {
        return prop.getProperty("app.url");
    }
    
    public int getExplicitWait() {
        return Integer.parseInt(prop.getProperty("explicit.wait", "10"));
    }
    
    public int getImplicitWait() {
        return Integer.parseInt(prop.getProperty("implicit.wait", "5"));
    }
    
    public int getPageLoadTimeout() {
        return Integer.parseInt(prop.getProperty("page.load.timeout", "20"));
    }
}
```

**Example Configuration File: `application-qa.properties`**

```properties
env=qa
app.url=https://qa.ecommerce.com
implicit.wait=5
explicit.wait=10
page.load.timeout=20
```

**Runtime Usage:**
```
-Dplatform=browserstack -Dbrowser=Chrome -Denv=qa
```

This lets the same feature suite run against a selected environment and platform.

### 6. BasePage — Page Object Model Base Class

BasePage provides common Selenium operations and explicit waits. Individual Page Objects encapsulate locators and page-specific actions.

```java
public class BasePage {
    
    protected WebDriver driver;
    protected WebDriverWait wait;
    
    public BasePage(WebDriver driver) {
        this.driver = driver;
        this.wait = new WebDriverWait(
            driver,
            Duration.ofSeconds(
                ConfigurationManager.getInstance().getExplicitWait()
            )
        );
    }
    
    protected void waitForElementVisible(By locator) {
        wait.until(ExpectedConditions.visibilityOfElementLocated(locator));
    }
    
    protected void waitForElementClickable(By locator) {
        wait.until(ExpectedConditions.elementToBeClickable(locator));
    }
    
    protected void click(By locator) {
        waitForElementClickable(locator);
        driver.findElement(locator).click();
    }
    
    protected void sendKeys(By locator, String text) {
        waitForElementVisible(locator);
        driver.findElement(locator).clear();
        driver.findElement(locator).sendKeys(text);
    }
}
```

**Example Page Object: LoginPage**

```java
public class LoginPage extends BasePage {
    
    private By usernameField = By.id("username");
    private By passwordField = By.id("password");
    private By loginButton = By.xpath("//button[@type='submit']");
    private By successMessage = By.className("success-msg");
    
    public LoginPage(WebDriver driver) {
        super(driver);
    }
    
    public void enterUsername(String username) {
        sendKeys(usernameField, username);
    }
    
    public void enterPassword(String password) {
        sendKeys(passwordField, password);
    }
    
    public void clickLoginButton() {
        click(loginButton);
    }
    
    public boolean isLoginSuccessful() {
        return driver.findElement(successMessage).isDisplayed();
    }
}
```

### 7. Step Definitions — Gherkin to Java Bridge

Step Definitions map Gherkin steps to Java methods. They should remain thin: receive data from the feature, call Page Object methods, and perform appropriate validation.

```java
public class LoginStepDefinition {
    
    private LoginPage loginPage;
    private WebDriver driver;
    
    @Given("user is on the login page")
    public void userIsOnLoginPage() {
        driver = StartDriver.getDriver();
        loginPage = new LoginPage(driver);
        driver.get(ConfigurationManager.getInstance().getApplicationUrl());
    }
    
    @When("user enters valid username")
    public void userEntersValidUsername() {
        loginPage.enterUsername("validuser@test.com");
    }
    
    @When("user enters valid password")
    public void userEntersValidPassword() {
        loginPage.enterPassword("password123");
    }
    
    @When("user clicks on login button")
    public void userClicksOnLoginButton() {
        loginPage.clickLoginButton();
    }
    
    @Then("user should be logged in successfully")
    public void userShouldBeLoggedInSuccessfully() {
        Assert.assertTrue(loginPage.isLoginSuccessful());
    }
}
```

### 8. Cucumber Feature File

Feature files describe business behavior rather than Selenium implementation details. Important: Feature files should not contain XPath, WebElement, sendKeys or Selenium implementation details—those belong in Page Objects and utilities.

```gherkin
Feature: Login functionality

  Scenario: Valid user login
    Given user is on the login page
    When user enters valid username
    And user enters valid password
    And user clicks on login button
    Then user should be logged in successfully

  Scenario: Login with invalid credentials
    Given user is on the login page
    When user enters username "invalid@example.com"
    And user enters password "wrongpass"
    And user clicks on login button
    Then user should see error message
```

## 4. Complete Execution Flow

The complete flow from Maven execution through to reports:

```
1. Jenkins / Developer starts Maven execution
   ↓
2. Cucumber Runner starts (@RunWith, @CucumberOptions)
   ↓
3. Feature file and scenario are selected
   ↓
4. @Before Hook executes (StartDriver.initializeDriver())
   ↓
5. Read -Dplatform and -Dbrowser system properties
   ↓
   ├─→ If platform=local
   │   └─→ LocalDriver.createDriver(browser)
   │       └─→ Creates ChromeDriver/FirefoxDriver/EdgeDriver
   │
   └─→ If platform=browserstack
       └─→ BSDriverHelper.createDriver(browser)
           └─→ Creates RemoteWebDriver with BrowserStack capabilities
   ↓
6. Step Definition @Given/@When/@Then methods execute
   ↓
7. Page Object methods are called (UI actions)
   ↓
8. Selenium actions and validations
   ↓
9. @After Hook executes
   ├─→ If scenario failed: captureScreenshot()
   └─→ StartDriver.quitDriver()
   ↓
10. Reports & Screenshots generated
```

## 5. Runtime Execution Matrix

Runtime arguments answer key questions:

- **-Dplatform:** "Where should the test execute?" (local / browserstack)
- **-Dbrowser:** "Which browser should be used?" (Chrome / Firefox / Edge)
- **-Denv:** "Which environment?" (qa / uat / prod)

| Command | Platform | Browser | Driver Type |
|---------|----------|---------|------------|
| `mvn clean test -Dplatform=local -Dbrowser=Chrome` | Local | Chrome | ChromeDriver |
| `mvn clean test -Dplatform=local -Dbrowser=Firefox` | Local | Firefox | FirefoxDriver |
| `mvn clean test -Dplatform=local -Dbrowser=Edge` | Local | Edge | EdgeDriver |
| `mvn clean test -Dplatform=browserstack -Dbrowser=Chrome` | BrowserStack | Chrome | RemoteWebDriver |
| `mvn clean test -Dplatform=browserstack -Dbrowser=Firefox` | BrowserStack | Firefox | RemoteWebDriver |
| `mvn clean test -Dplatform=browserstack -Dbrowser=Edge` | BrowserStack | Edge | RemoteWebDriver |

## 6. Cross-Browser Testing with BrowserStack

The same Cucumber feature and Step Definitions can run against multiple browsers. BrowserStack provides the remote execution layer; BSDriverHelper translates the selected browser into BrowserStack capabilities.

```
SAME FEATURE FILE
    ↓
    +────────────────────────────────────────┐
    ↓                                        ↓
Local execution                    BrowserStack execution
    ↓                                        ↓
LocalDriver                         BSDriverHelper
    ↓                                        ↓
    +──────────┬──────────┬──────────────────+──────────┬──────────┐
    ↓          ↓          ↓                  ↓          ↓          ↓
  Chrome   Firefox      Edge                Chrome    Firefox     Edge
```

**Key Benefit:** Business scenarios should not be duplicated merely because the execution browser changes. The same `.feature` file and Step Definitions work across all browsers and platforms.

## 11. Why This Architecture?

### 1. **Separation of Concerns**
- Feature files describe business scenarios
- Step Definitions map Gherkin steps to Java
- Page Objects handle UI element actions
- Drivers handle execution infrastructure

### 2. **Easy Platform Switching**
- StartDriver hides whether execution is local or BrowserStack
- No changes required to feature files or Step Definitions

### 3. **Cross-Browser Support**
- Browser can be changed through `-Dbrowser` system property
- Same feature runs across Chrome, Firefox, Edge
- No feature duplication needed

### 4. **Maintainability**
- BrowserStack-specific capabilities remain inside BSDriverHelper
- Locators isolated in Page Objects
- Configuration externalized

### 5. **Scenario Lifecycle**
- Cucumber Hooks are a better fit than TestNG BaseTest
- Setup/teardown tied naturally to each scenario
- No test class inheritance needed

### 6. **Parallel Execution Ready**
- ThreadLocal WebDriver isolates driver instances per thread
- Each parallel scenario gets its own WebDriver
- Supports distributed/concurrent test execution

## 12. Interview-Ready Explanation

**The 30-Second Elevator Pitch:**

"Our framework is a Java Selenium hybrid framework based on Cucumber BDD and Page Object Model. The business scenarios are maintained in Cucumber feature files, and Step Definitions map those Gherkin steps to Page Object methods. We use Cucumber Hooks for common scenario setup and teardown. Driver management is centralized through a StartDriver class. At runtime, StartDriver reads the platform and browser system properties. If platform is local, it delegates driver creation to LocalDriver; if platform is BrowserStack, it delegates to BSDriverHelper, which creates a RemoteWebDriver with BrowserStack capabilities. This allows the same feature and automation code to run locally or on BrowserStack across Chrome, Firefox and Edge. Environment-specific values are externalized through configuration, and Jenkins passes runtime parameters to Maven for CI/CD execution."
