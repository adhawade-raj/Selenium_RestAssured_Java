# BDD Mapping — Step Definitions (Cucumber Runner) & Framework Integration

**Note**: This document describes a BDD/Cucumber approach adapted from **1.1-RestAssured_Framework_Guide.md**. For the primary framework approach (pure TestNG-based), refer to **1.1** and **1.2**. This BDD pattern uses **Cucumber Runner** with **Hooks** instead of BaseTest and JUnit DataProvider, allowing Scenario Outlines for data-driven testing.

---

## Framework Integration

The BDD/Cucumber approach shares the **same core framework layers** as the TestNG framework:
- **Configuration Manager** — Reads environment & test data config (including environment-specific datasets)
- **RestClient** — HTTP abstraction layer (from 1.1)
- **Authentication & Prerequisite Layer** — Token and test data management (implemented via Hooks)
- **Utilities, Constants & Enums** — Shared helpers (from 1.1)
- **TestContext** — Replaces BaseTest; manages shared state per scenario

The primary difference is the **test execution style**: BDD uses human-readable Gherkin scenarios (Scenario Outlines) and step definitions instead of TestNG `@Test` methods with DataProviders.

**Key Differences from 1.1 (TestNG):**
- ✗ **No JUnit DataProvider** — Data-driven testing via Scenario Outlines with Examples in .feature files
- ✓ **Cucumber Runner** — Executes feature files via Cucumber CLI or Maven runner
- ✓ **Hooks** — @Before/@After annotations (Cucumber-style) replace BaseTest @BeforeTest/@AfterTest
- ✓ **TestContext (PicoContainer DI)** — Injected into step definitions; holds shared state

#### 3. ConfigurationManager Implementation

```java
public class ConfigurationManager {
    private Properties prop;
    private String env;        // SCT or MCT-AND-CERT
    private String channel;    // MOB or EXT
    
    public Properties initProp() {
        // Get environment from system properties, default to SCT
        String envName = System.getProperty("env", "SCT");
        String channelName = System.getProperty("test.data.channel", "MOB");
        
        prop = new Properties();
        String propFile = "application-" + envName.toLowerCase() + ".properties";
        InputStream input = getClass().getClassLoader()
            .getResourceAsStream(propFile);
        
        if (input != null) {
            prop.load(input);
        }
        
        this.env = envName;
        this.channel = channelName;
        
        return prop;
    }
    
    public String getTestDataPath() {
        // Returns path like: src/test/resources/testdata/SCT/MOB/
        return "src/test/resources/testdata/" + env + "/" + channel + "/";
    }
    
    public String getEnvironment() {
        return env;
    }
    
    public String getChannel() {
        return channel;
    }
}
```

#### 4. Hook Example Using Environment

```java
public class Hooks {
    private TestContext context;
    private ConfigurationManager configManager;
    
    public Hooks(TestContext context) {
        this.context = context;
        this.configManager = new ConfigurationManager();
    }
    
    @Before
    public void beforeScenario(Scenario scenario) {
        System.out.println("=== Starting Scenario: " + scenario.getName() + " ===");
        
        // Initialize properties
        configManager.initProp();
        
        System.out.println("Environment: " + configManager.getEnvironment());
        System.out.println("Channel: " + configManager.getChannel());
        System.out.println("Test Data Path: " + configManager.getTestDataPath());
        
        // Initialize RestClient with environment-specific base URL
        String baseUrl = getBaseUrlForEnvironment(configManager.getEnvironment());
        context.setRestClient(new RestClient(configManager.initProp(), baseUrl));
        
        // Authenticate user
        authenticateUser();
    }
    
    @After
    public void afterScenario(Scenario scenario) {
        System.out.println("=== Completed Scenario: " + scenario.getName() + " ===");
        // Cleanup
    }
    
    private String getBaseUrlForEnvironment(String env) {
        if ("SCT".equalsIgnoreCase(env)) {
            return "https://api-sct.example.com/v1";
        } else if ("MCT-AND-CERT".equalsIgnoreCase(env)) {
            return "https://api-mct.example.com/v1";
        }
        return "https://api.example.com/v1";
    }
    
    private void authenticateUser() {
        // Authentication logic
    }
}
```

#### 5. Loading Test Data Based on Environment & Channel

```java
public class UserStepDefinitions {
    private TestContext context;
    private ConfigurationManager configManager;
    
    public UserStepDefinitions(TestContext context) {
        this.context = context;
        this.configManager = new ConfigurationManager();
    }
    
    @Given("I load users from test data for current environment")
    public void loadUsersFromTestData() {
        String testDataPath = configManager.getTestDataPath();
        String testDataFile = testDataPath + "users.xlsx";
        
        List<Map<String, String>> userData = ExcelUtility.readTestData(
            testDataFile,
            "Users"
        );
        
        context.putData("testUsers", userData);
        System.out.println("Loaded " + userData.size() + " users from " + testDataFile);
    }
    
    @When("I create a user from test data")
    public void createUserFromTestData() {
        List<Map<String, String>> testUsers = 
            (List<Map<String, String>>) context.getData("testUsers");
        
        for (Map<String, String> userData : testUsers) {
            CreateUserRequest request = new CreateUserRequest();
            request.setName(userData.get("Name"));
            request.setEmail(userData.get("Email"));
            request.setMobile(userData.get("Mobile"));
            
            Response response = context.getRestClient()
                .post("/users", "application/json", request, true, true);
            
            context.setLastResponse(response);
            context.putData("createdUserId", response.jsonPath().getString("id"));
        }
    }
}
```

### Key Points

#### Environment Variable Mapping

| Variable | Value | Usage |
|---|---|---|
| `env` | `SCT` or `MCT-AND-CERT` | Selects property file and testdata folder |
| `test.data.channel` | `MOB` or `EXT` | Selects test data subfolder within environment |

#### Property File Naming Convention

```
application-{env_lowercase}.properties

Example:
  - application-sct.properties
  - application-mct-and-cert.properties
```

#### Test Data Path Construction

```
src/test/resources/testdata/{env}/{channel}/

Example:
  - src/test/resources/testdata/SCT/MOB/
  - src/test/resources/testdata/SCT/EXT/
  - src/test/resources/testdata/MCT-AND-CERT/MOB/
  - src/test/resources/testdata/MCT-AND-CERT/EXT/
```

### MCT-AND-CERT Special Case

**Note:** MCT (Mobile Conformance Test) and CERT (Certification) environments share the same test data.
- Single folder: `MCT-AND-CERT/` contains both MOB and EXT data
- Both test scenarios (mobile conformance + certification) use the same datasets
- Ensures consistency and reduces test data maintenance overhead

## High-level Design (Same Layered Architecture as 1.1)

```
┌─────────────────────────────────────────────────────────┐
│         Feature Files (Gherkin Scenarios)               │  <- Human-readable test cases
├─────────────────────────────────────────────────────────┤
│  Step Definitions (lightweight glue code)               │  <- Maps Gherkin steps to Java methods
├─────────────────────────────────────────────────────────┤
│  TestContext (PicoContainer DI)                         │  <- Replaces BaseTest; holds shared state
├─────────────────────────────────────────────────────────┤
│  Hooks (@Before, @After)                                │  <- Setup/teardown, auth, env selection
├─────────────────────────────────────────────────────────┤
│   RestClient (GET/POST/PUT/PATCH/DELETE)               │  <- Same as 1.1 (from core layer)
├─────────────────────────────────────────────────────────┤
│   Configuration Manager & Test Data Provider            │  <- Reads env & testdata by env/channel
├─────────────────────────────────────────────────────────┤
│    Utilities, Constants & Enums                         │  <- Shared with 1.1
├─────────────────────────────────────────────────────────┤
│         Cucumber Runner                                  │  <- Executes feature files
└─────────────────────────────────────────────────────────┘
```

## Component Mapping to 1.1

| 1.1 (TestNG) | 2.1 (BDD/Cucumber) | Notes |
|---|---|---|
| BaseTest class | Hooks + TestContext | @Before/@After for setup/teardown |
| @Test methods | Feature file steps (Given/When/Then) | Gherkin replaces test method names |
| @DataProvider | Scenario Outline with Examples | Data driven via feature file tables |
| @BeforeMethod/@AfterMethod | @Before/@After hooks | Cucumber-style setup/cleanup |
| ConfigurationManager | ConfigurationManager (same) | Synced from 1.1 |
| RestClient | RestClient (same) | Reused from 1.1 core layer |
| Service classes | Step Definitions | Call RestClient & perform assertions |
| Properties files | Properties + Environment enum | Reads by env (SCT, MCT-AND-CERT) |

### 3. TestContext (replaces BaseTest)
**Purpose**: Hold shared state across step definitions within a scenario

```java
public class TestContext {
    private Properties prop;
    private RestClient restClient;
    private Response lastResponse;
    private String token;
    private Map<String, Object> sharedData = new HashMap<>();
    
    public TestContext(ConfigurationManager config) {
        this.prop = config.initProp();
        this.restClient = new RestClient(prop, getBaseUri());
    }
    
    // Getters/setters for shared state
    public void setToken(String token) { this.token = token; }
    public String getToken() { return token; }
    public void setLastResponse(Response response) { this.lastResponse = response; }
    public Response getLastResponse() { return lastResponse; }
    public void putData(String key, Object value) { sharedData.put(key, value); }
    public Object getData(String key) { return sharedData.get(key); }
}
```

### 4. Hooks (replaces BaseTest @BeforeTest/@AfterTest)
**Purpose**: Setup authentication, initialize TestContext per scenario

```java
public class Hooks {
    private TestContext context;
    private ConfigurationManager configManager;
    
    public Hooks(TestContext context) {
        this.context = context;
        this.configManager = new ConfigurationManager();
    }
    
    @Before
    public void beforeScenario(Scenario scenario) {
        System.out.println("Starting scenario: " + scenario.getName());
        // Initialize environment
        configManager.initProp();
        // Authenticate and store token
        authenticateUser();
    }
    
    @After
    public void afterScenario(Scenario scenario) {
        System.out.println("Completed scenario: " + scenario.getName());
        // Cleanup (delete created data, logout, etc.)
    }
    
    private void authenticateUser() {
        // Call login endpoint via RestClient
        // Store token in TestContext
        String token = context.getRestClient().authenticate();
        context.setToken(token);
    }
}
```

### 5. Step Definitions
**Purpose**: Lightweight glue code mapping Gherkin steps to Java logic

Example: User API step definitions

```java
public class UserStepDefinitions {
    private TestContext context;
    private RestClient restClient;
    
    public UserStepDefinitions(TestContext context) {
        this.context = context;
        this.restClient = context.getRestClient();
    }
    
    @Given("I have a valid user with email {string}")
    public void prepareUser(String email) {
        CreateUserRequest request = new CreateUserRequest();
        request.setEmail(email);
        request.setName("Test User");
        context.putData("email", email);
    }
    
    @When("I create a new user")
    public void createUser() {
        CreateUserRequest request = (CreateUserRequest) context.getData("userRequest");
        Response response = restClient.post("/users", "application/json", request, true, true);
        context.setLastResponse(response);
    }
    
    @Then("the response status code should be {int}")
    public void verifyStatusCode(int expectedCode) {
        Response response = context.getLastResponse();
        assertEquals(response.getStatusCode(), expectedCode);
    }
}
```

## Setting Request Body in Step Definitions

### Option A: Setting Body via Gherkin Parameters (Data Tables / Examples)

Feature file with URL and body parameters:
```gherkin
Feature: User API Management

  Scenario Outline: Create user via POST request with body
    Given the base URL is "<baseUrl>"
    When I send a POST request for "<endpoint>" with body "<requestBody>"
    Then the response status code should be <statusCode>
    And the response should contain "<expectedField>"

    Examples:
      | baseUrl              | endpoint | requestBody                                              | statusCode | expectedField |
      | https://api.qa.com   | /users   | {"name":"John","email":"john@example.com","role":"user"} | 201        | id            |
      | https://api.qa.com   | /users   | {"name":"Jane","email":"jane@example.com","role":"admin"}| 201        | id            |
```

Step definition implementation:
```java
public class UserStepDefinitions {
    private TestContext context;
    private RestClient restClient;
    private String baseUrl;
    
    public UserStepDefinitions(TestContext context) {
        this.context = context;
        this.restClient = context.getRestClient();
    }
    
    @Given("the base URL is {string}")
    public void setBaseUrl(String url) {
        this.baseUrl = url;
        // Create RestClient with dynamic baseURI
        this.restClient = new RestClient(context.getProp(), url);
        context.setRestClient(restClient);
    }
    
    @When("I send a POST request for {string} with body {string}")
    public void sendPostRequestWithBody(String endpoint, String requestBody) {
        Response response = restClient.post(
            endpoint,
            "application/json",
            requestBody,
            true,
            true
        );
        context.setLastResponse(response);
    }
}
```

### Updated TestContext for RestClient Management

```java
public class TestContext {
    private Properties prop;
    private RestClient restClient;
    private Response lastResponse;
    private String token;
    private Map<String, Object> sharedData = new HashMap<>();
    
    public TestContext(ConfigurationManager config) {
        this.prop = config.initProp();
        String defaultBaseUri = prop.getProperty("base.url");
        this.restClient = new RestClient(prop, defaultBaseUri);
    }
    
    public RestClient getRestClient() { return restClient; }
    
    public void setRestClient(RestClient restClient) { 
        this.restClient = restClient; 
    }
    
    public Properties getProp() { return prop; }
    
    public void setLastResponse(Response response) { 
        this.lastResponse = response; 
    }
    
    public Response getLastResponse() { return lastResponse; }
    
    public void setToken(String token) { this.token = token; }
    
    public String getToken() { return token; }
    
    public void putData(String key, Object value) { 
        sharedData.put(key, value); 
    }
    
    public Object getData(String key) { return sharedData.get(key); }
}
```

## Summary

**2.1 (BDD/Cucumber) vs 1.1 (TestNG):**

| Feature | 1.1 | 2.1 |
|---|---|---|
| Test Execution | `@Test` methods + TestNG runner | Feature files + Cucumber runner |
| Data-Driven | `@DataProvider` | Scenario Outline with Examples |
| Setup/Teardown | `BaseTest` + `@BeforeTest/@AfterTest` | `Hooks` + `@Before/@After` |
| State Sharing | BaseTest class fields | TestContext (PicoContainer DI) |
| Test Runner | TestNG suite XML | Cucumber Runner + Maven |
| Environment Support | ✓ (property-based) | ✓ (SCT, MCT-AND-CERT + MOB/EXT channels) |
| Readability | Java code | Gherkin (human-readable) |
| RestClient | ✓ (same layer) | ✓ (reused) |
| ConfigManager | ✓ (same layer) | ✓ (enhanced for testdata paths) |

Both frameworks leverage the same **core RestClient, ConfigurationManager, and utility layers** from 1.1, ensuring consistency and code reuse.
