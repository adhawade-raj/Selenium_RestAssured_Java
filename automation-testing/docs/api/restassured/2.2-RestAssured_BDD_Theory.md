# BDD API Automation Framework — Theory

We have designed our BDD API automation framework using **Java, Rest Assured, Cucumber, and TestNG**. The framework follows a **layered architecture** with **BDD/Gherkin syntax** to keep responsibilities clear, tests maintainable, and scenarios readable by non-technical stakeholders. For detailed implementation guidance, refer to **2.1-RestAssured_BDD_StepDefinitions.md**.

## Core Components

- **Feature Files (Gherkin Scenarios)**
  - Human-readable test cases written in Given-When-Then format.
  - Supports Scenario Outlines with Examples for data-driven testing.
  - Organized by feature domain (user_management.feature, auth.feature, etc.).
  - Can be tagged (@smoke, @regression, @critical) for selective execution.

- **Step Definitions**
  - Lightweight glue code mapping Gherkin steps to Java methods.
  - Organized by domain (UserStepDefinitions, AuthStepDefinitions).
  - Delegate actual test logic to RestClient and utility layers.
  - Keep implementations focused and reusable across scenarios.

- **TestContext (State Management)**
  - Replaces BaseTest; holds shared state per scenario.
  - Injected via PicoContainer dependency injection into step definitions and hooks.
  - Thread-safe and scoped to individual scenarios.
  - Manages RestClient, response objects, tokens, and shared test data.

- **Hooks (@Before/@After)**
  - Replaces BaseTest @BeforeTest/@AfterTest lifecycle methods.
  - `@Before` — Initializes ConfigurationManager, authenticates users, sets up RestClient.
  - `@After` — Performs cleanup (deletes created data, logs scenario results).
  - Receives Scenario object to access scenario name and tags.

- **Configuration Manager**
  - Reads environment-specific configuration (SCT, MCT-AND-CERT).
  - Selects test data by environment and channel (MOB, EXT).
  - Loads property files (application-sct.properties, application-mct.properties).
  - Constructs test data paths dynamically.

- **RestClient (common HTTP layer)**
  - Encapsulates Rest Assured request execution for GET, POST, PUT, PATCH, and DELETE.
  - Builds RequestSpecification with headers, authentication, content-type, and query parameters.
  - Manages authorization header injection and logging.
  - Same implementation as 1.1 framework; reused in 2.1 BDD.

- **Prerequisite / Authentication Layer**
  - Invokes authentication APIs when required; retrieves and caches access tokens.
  - Exposes tokens to subsequent requests via RestClient.
  - Handles token refresh and expiry concerns.
  - Implemented via Hooks and TestContext (replaces BaseTest).

- **Payloads and Mapping**
  - Request and response payloads are modeled as POJOs using **Lombok** to reduce boilerplate.
  - **Jackson Databind** is used for JSON serialization/deserialization.
  - Same models as 1.1 framework; reused in 2.1 BDD.

- **Data-driven Testing**
  - **Scenario Outline with Examples** — Primary approach; data embedded in feature files.
  - **Excel Utility** — Alternative approach for external test data management.
  - **ExcelUtility** provides multiple combinations of test data to drive scenarios.
  - Tests run multiple times with different inputs from Examples tables or external files.

- **Utilities, Constants and Enums**
  - Reusable helpers (ExcelUtility, JsonPathValidator, StringUtils) live in a common utilities package to avoid duplication.
  - Domain enums (APIHttpStatus, APIConstants) centralize shared resources.
  - Same utilities as 1.1 framework; reused in 2.1 BDD.

- **Reporting**
  - **Allure** is used for comprehensive test reporting.
  - Request/response bodies and headers are logged automatically via `RestAssured.filters(new AllureRestAssured())`.
  - Execution artifacts are produced under `allure-results/`, used to generate interactive HTML reports.
  - Custom steps can be marked with `@Step` annotations in step definitions.
  - Gherkin scenarios are automatically linked to test results.

- **Cucumber Runner**
  - Executes feature files via Cucumber JUnit Platform engine.
  - Configures glue paths to locate step definitions and hooks.
  - PicoContainer provides dependency injection for TestContext across step definitions.
  - Supports Maven CLI with tag filters and environment parameters.

- **Environment & Channel Support**
  - Environments: SCT (System Capability Test), MCT-AND-CERT (Mobile Conformance Test & Certification).
  - Channels: MOB (Mobile), EXT (External/Web API).
  - ConfigurationManager resolves test data paths by environment and channel.
  - Same property-based approach as 1.1; enhanced for BDD scenarios.

## Design Principles

- **Reusability** — Common utilities, constants, and RestClient methods shared across all tests and step definitions.
- **Readability** — Gherkin scenarios read like plain English; non-technical stakeholders can understand test intent.
- **Maintainability** — Centralized configuration, layered architecture, and DRY principles reduce change impact.
- **Scalability** — Layered architecture supports thousands of scenarios; tag-based filtering enables selective execution.
- **Reliability** — Token refresh logic, error handling, comprehensive logging, and state isolation per scenario.
- **Modularity** — Step definitions are loosely coupled; scenarios can reuse steps across features.
- **Traceability** — Allure reports link Gherkin steps to test evidence (logs, screenshots, response bodies).

## BDD vs TestNG (2.1 vs 1.1) Comparison

| Aspect | 1.1 (TestNG) | 2.1 (BDD) | Benefit |
|--------|---|---|---|
| **Test Authoring** | Java `@Test` methods | Gherkin Given-When-Then | Better readability; stakeholder collaboration |
| **Data-Driven** | `@DataProvider` | Scenario Outline + Examples | Cleaner data management; BDD-aligned |
| **Setup/Teardown** | BaseTest + `@BeforeTest/@AfterTest` | Hooks + `@Before/@After` | Thread-safe state per scenario |
| **State Management** | BaseTest class fields | TestContext (PicoContainer DI) | Cleaner, more testable |
| **Test Runner** | TestNG XML suite | Cucumber Runner + Maven | Tag-based filtering; better CI/CD integration |
| **Reporting** | Allure (same layer) | Allure + Gherkin mapping | Enhanced traceability |
| **Code Reuse** | RestClient, ConfigManager, Utilities | RestClient, ConfigManager, Utilities (reused) | No duplication; consistent patterns |

This concise overview is useful for explaining the BDD framework architecture and design choices. For detailed patterns, code examples, and best practices, refer to **2.1-RestAssured_BDD_StepDefinitions.md**.
