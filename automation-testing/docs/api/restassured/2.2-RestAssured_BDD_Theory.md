# BDD API Automation Framework — Architecture & Implementation

Our BDD API automation framework is a **hybrid framework** built with **Java, Rest Assured, Cucumber, and TestNG**. This document explains the technical architecture, components, and technologies we used to build it.

## Framework Layers & Components

### 1. Feature Files Layer (Gherkin)
- Scenarios written in Given-When-Then format
- Supports Scenario Outlines with Examples for parameterized test data
- Tagged with @smoke, @regression, @critical for selective test execution
- Organized by feature (user_management.feature, auth.feature, etc.)

### 2. Step Definitions Layer
- Maps Gherkin steps to executable Java code
- Organized by domain (UserStepDefinitions, AuthStepDefinitions)
- Delegates business logic to RestClient and utility layers

### 3. TestContext & Dependency Injection (PicoContainer)
- Manages scenario-specific state (RestClient, API responses, auth tokens, test data)
- Injected into step definitions via PicoContainer
- Thread-safe and isolated per scenario

### 4. Hooks (@Before/@After)
- `@Before` — Initializes ConfigurationManager, sets up RestClient, handles authentication
- `@After` — Performs cleanup (deletes test data, logs results)
- Receives Scenario object for conditional execution based on tags

### 5. RestClient Layer
- Encapsulates REST API calls (GET, POST, PUT, PATCH, DELETE)
- Builds RequestSpecification with headers, auth tokens, content-type, query parameters
- Manages authorization headers and logging
- Reused from 1.1 framework (no code duplication)

### 6. Authentication & Configuration
- **ConfigurationManager** — Loads environment-specific configs (SCT, MCT-AND-CERT) and channel-specific data (MOB, EXT)
- **Authentication Layer** — Retrieves and caches auth tokens for API requests
- Token refresh and expiry handling built-in

### 7. Data Models (POJOs)
- Request/response objects modeled as Java POJOs with **Lombok** (reduces boilerplate)
- **Jackson Databind** used for JSON serialization/deserialization
- Reused from 1.1 framework

### 8. Data-Driven Testing
- **Scenario Outline with Examples** — Data embedded directly in feature files
- **Excel Utility** — External test data source for large datasets
- Same approach as 1.1 framework

### 9. Utilities & Constants
- Common helpers: ExcelUtility, JsonPathValidator, StringUtils, etc.
- Domain enums: APIHttpStatus, APIConstants, etc.
- Centralized in utilities package (reused from 1.1)

### 10. Reporting Layer
- **Allure** used for comprehensive HTML test reports
- Rest Assured responses automatically captured via AllureRestAssured filter
- Custom @Step annotations in step definitions
- Gherkin steps automatically linked to test results

### 11. Cucumber Runner
- Executes feature files using Cucumber JUnit Platform engine
- Configures glue paths for step definitions and hooks
- PicoContainer provides dependency injection for TestContext
- Maven CLI supports tag filtering and environment parameters

## How We Built It (Framework Architecture)

### Design Decision: Reuse from 1.1 Framework
We built the BDD framework by **reusing and extending** the 1.1 (TestNG) framework:
- **RestClient** — Reused as-is; same HTTP request/response handling
- **Data Models (POJOs)** — Reused; no code duplication
- **Utilities & Constants** — Reused; ExcelUtility, JsonPathValidator, APIConstants
- **Configuration Manager** — Reused; same environment/channel resolution
- **Authentication Logic** — Reused; token caching and refresh

### New Components for BDD
We added these new layers on top:
- **Feature Files** — Gherkin test scenarios in Given-When-Then format
- **Step Definitions** — Java methods that map Gherkin steps to RestClient calls
- **Hooks** — @Before/@After lifecycle management (replaces BaseTest)
- **TestContext** — Per-scenario state management via PicoContainer DI

### Integration Points
1. Step Definitions → RestClient (for API calls)
2. Step Definitions → ConfigurationManager (for test data and environments)
3. Hooks → TestContext (for scenario setup/teardown)
4. All Requests → AllureRestAssured filter (automatic reporting)

## Environment & Data Strategy

**Supported Environments:**
- SCT (System Capability Test)
- MCT-AND-CERT (Mobile Conformance Test & Certification)

**Supported Channels:**
- MOB (Mobile apps)
- EXT (External/Web APIs)

**Data Management:**
- Property files per environment: `application-sct.properties`, `application-mct.properties`
- Channel-specific test data paths resolved at runtime
- ConfigurationManager handles all path construction
