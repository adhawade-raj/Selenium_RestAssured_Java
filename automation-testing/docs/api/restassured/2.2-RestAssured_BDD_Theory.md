# BDD API Automation Framework — Interview Ready Overview

## 1. Framework Overview

* Our API automation framework is a **BDD-based API automation framework** built using:

  * **Java**
  * **Rest Assured**
  * **Cucumber**
  * **Cucumber JUnit**
  * **PicoContainer**
  * **Jackson**
  * **Lombok**
  * **Apache POI**
  * **Allure**
  * **Maven**

* The framework follows a **layered architecture**, where each component has a specific responsibility.

* The framework was developed by **reusing the common components from our existing 1.1 API automation framework** and adding the BDD layer on top.

# 3. Feature File Layer — BDD

* Feature files are written using **Gherkin syntax**.
* We follow the standard BDD structure:

```gherkin
Feature: User API Validation

  Scenario: Create a new user

    Given the user has valid authentication
    When the user sends a POST request to create a user
    Then the response status code should be 201
    And the response should contain the created user details
```

* The feature file contains the **business-readable test scenario**.
* It does not contain Java implementation logic.
* Feature files are organized based on business/API functionality.

### Scenario Outline

* For data-driven scenarios, we use **Scenario Outline** with an `Examples` table.

```gherkin
Scenario Outline: Validate user creation

  Given the user has valid authentication
  When the user sends a POST request with "<userType>"
  Then the response status code should be <statusCode>

Examples:
  | userType | statusCode |
  | ADMIN    | 201        |
  | CUSTOMER | 201        |
```

* This is the BDD equivalent of parameterized execution.
* We do **not use TestNG `@DataProvider`** in this framework.

---

# 4. Step Definition Layer

* Step Definitions contain the Java implementation corresponding to the Gherkin steps.
* Cucumber maps each Given/When/Then step to its corresponding Java method.

Example:

```java
@When("the user sends a POST request to create a user")
public void createUser() {

    response = restClient.post(
        requestBody,
        "/users"
    );
}
```

* Step Definitions should primarily coordinate the test flow.
* Business/API implementation is delegated to reusable framework components such as:

  * `RestClient`
  * `ConfigurationManager`
  * POJOs
  * Utility classes

### Responsibility

```text
Feature File
     ↓
Step Definition
     ↓
Framework Component
     ↓
API
```

This keeps the step definitions clean and maintainable.

---

# 5. TestContext — Scenario-Level State Management

* Since Cucumber scenarios may contain multiple step definitions, we need a way to share data between steps.
* We use a **TestContext** class for maintaining scenario-specific data.

Example data maintained in TestContext:

```text
RestClient
Request Object
Response
Access Token
User ID
Test Data
Other scenario-specific values
```

* **PicoContainer** is used for dependency injection.
* TestContext is injected into the required Step Definition classes.

Example:

```java
public class UserStepDefinitions {

    private TestContext testContext;

    public UserStepDefinitions(TestContext testContext) {
        this.testContext = testContext;
    }
}
```

### Why TestContext?

Without TestContext, we would need to maintain scenario data using static variables or duplicate objects across step definitions.

TestContext provides:

* Scenario-level data sharing
* Better isolation
* Cleaner step definitions
* Reduced use of static variables
* Dependency injection through PicoContainer

# 6. Cucumber Hooks

* Cucumber Hooks are used for **setup and teardown activities**.
* We use:

```java
@Before
@After
```

### `@Before`

Executed before each scenario.

Typical activities:

* Initialize configuration
* Initialize RestClient
* Prepare authentication
* Load required test data
* Perform prerequisite setup

Example:

```java
@Before
public void setUp() {

    configurationManager = new ConfigurationManager();

    restClient = new RestClient(
        configurationManager
    );
}
```

### `@After`

Executed after each scenario.

Typical activities:

* Cleanup test data
* Capture scenario result
* Perform required post-processing
* Attach required information to the report

Example:

```java
@After
public void tearDown(Scenario scenario) {

    // cleanup
    // logging
    // reporting
}
```

### Important Interview Point

In our BDD framework, **Cucumber Hooks perform the role that a BaseTest class commonly performs in a TestNG-based framework**.

We therefore don't need to extend a `BaseTest` class from our Cucumber step definitions.

---

# 7. Authentication Layer

* Authentication is handled centrally rather than being implemented separately inside every test.
* Before executing APIs that require authentication, the framework obtains the required access token.
* The token can then be passed to the RestClient for subsequent API calls.

Typical flow:

```text
Scenario
   ↓
@Before Hook
   ↓
Authentication
   ↓
Access Token
   ↓
TestContext
   ↓
RestClient
   ↓
API Request
```

### Benefits

* Avoids duplicate authentication code.
* Keeps authentication logic separate from business test logic.
* Makes token handling reusable across APIs.
* Supports token caching/refresh where required.

# 8. Configuration Manager

* `ConfigurationManager` is responsible for reading and resolving environment-specific configuration.
* Configuration is maintained outside the test code.

Example configuration:

```text
application-sct.properties
application-mct.properties
```

### Supported Environments

* **SCT** — System Capability Test
* **MCT-AND-CERT** — Mobile Conformance Test & Certification

### Supported Channels

* **MOB** — Mobile
* **EXT** — External/Web APIs

The framework resolves the required configuration based on the selected environment and channel.

Example:

```text
Environment
     +
Channel
     ↓
ConfigurationManager
     ↓
Environment-specific properties
     ↓
Base URL / credentials / paths / test data
```

This allows the same automation code to execute against different environments without hardcoding URLs.

# 9. RestClient Layer

* `RestClient` is the central component responsible for communicating with the APIs.
* It encapsulates Rest Assured implementation.

It supports common HTTP operations:

```text
GET
POST
PUT
PATCH
DELETE
```

### RestClient Responsibilities

* Create `RequestSpecification`
* Configure base URI
* Add headers
* Add authentication
* Add query parameters
* Add path parameters
* Add request body
* Execute API request
* Capture API response
* Configure request/response logging

Example concept:

```java
RequestSpecification requestSpec =
        RestAssured
            .given()
            .baseUri(baseUri)
            .header("Authorization", token)
            .contentType(ContentType.JSON);
```

Then based on the requirement:

```java
GET
POST
PUT
PATCH
DELETE
```

is executed using the RestClient.

### Important Design Decision

The RestClient was **reused from our existing 1.1 framework**.

This avoided:

* Duplicate HTTP implementation
* Duplicate authentication handling
* Duplicate request configuration
* Duplicate logging logic

The BDD layer simply consumes the existing RestClient.

# 10. Request & Response POJOs

* API request and response payloads are represented using Java **POJO classes**.
* We use **Lombok** to reduce boilerplate code.

For example:

```java
@Data
public class UserRequest {

    private String name;
    private String email;
    private String userType;
}
```

Lombok can generate:

```text
Getters
Setters
Constructors
toString()
equals()
hashCode()
```

based on the annotations used.

---

# 11. Jackson Databind

* **Jackson Databind** is used for JSON serialization and deserialization.

### Serialization

Converting Java object → JSON.

```text
POJO
 ↓
Jackson
 ↓
JSON Request Body
```

Example:

```java
ObjectMapper mapper = new ObjectMapper();

String jsonBody =
        mapper.writeValueAsString(userRequest);
```

### Deserialization

Converting JSON response → Java object.

```text
JSON Response
 ↓
Jackson
 ↓
Response POJO
```

This allows us to work with strongly typed Java objects instead of manually creating JSON strings.

# 12. Data-Driven Testing

Our BDD framework supports multiple ways of managing test data.

### 1. Scenario Outline

For smaller and directly business-readable datasets:

```gherkin

Examples:
  | userType | expectedStatus |
  | ADMIN    | 201             |
  | CUSTOMER | 201             |
```

### 2. Excel Utility

* For larger or externally maintained datasets, we use an Excel utility.
* Apache POI is used to read Excel data.
* The utility converts Excel data into a structure that can be consumed by the test.

### Important Interview Point

We do **not use TestNG `@DataProvider`** because this is a **Cucumber JUnit BDD framework**.

Data-driven execution is primarily handled through:

```text
Scenario Outline + Examples
```

and, where required:

```text
Excel Utility
```

# 15. Allure Reporting

* **Allure** is used for test execution reporting.
* It provides a detailed HTML report containing:

  * Feature/scenario information
  * Step execution
  * Pass/fail status
  * Request/response information
  * Execution details

### Rest Assured + Allure

The `AllureRestAssured` filter can automatically capture Rest Assured request and response information.

Conceptually:

```text
Cucumber Scenario
       ↓
Step Definition
       ↓
RestClient
       ↓
Rest Assured
       ↓
AllureRestAssured Filter
       ↓
Allure Report
```

This makes API failures easier to debug because the request and response can be inspected from the report.

# 19. End-to-End Execution Flow

The complete execution flow can be explained in an interview as follows:

```text
1. Maven starts the test execution
             ↓
2. Cucumber JUnit starts
             ↓
3. Cucumber reads the Feature File
             ↓
4. Scenario is identified
             ↓
5. @Before Hook is executed
             ↓
6. ConfigurationManager loads environment configuration
             ↓
7. Authentication is initialized
             ↓
8. TestContext is created/injected through PicoContainer
             ↓
9. Given / When / Then steps are executed
             ↓
10. Step Definition calls RestClient
             ↓
11. RestClient creates RequestSpecification
             ↓
12. Request is sent using Rest Assured
             ↓
13. API response is received
             ↓
14. Response is stored in TestContext
             ↓
15. Response is validated
             ↓
16. Allure captures execution/request/response information
             ↓
17. @After Hook performs cleanup
             ↓
18. Allure report is generated
```

# 20. How to Explain the Framework in an Interview

A concise interview explanation can be:

> "We have built a BDD-based API automation framework using Java, Rest Assured, Cucumber and JUnit. The framework follows a layered architecture. Feature files contain our business scenarios in Given-When-Then format, and Step Definitions map those steps to Java implementation.
>
> We use Cucumber Hooks for scenario-level setup and teardown, instead of a TestNG BaseTest. TestContext is used to maintain scenario-specific state such as RestClient, response and authentication information, and PicoContainer provides dependency injection between step definition classes.
>
> The actual API communication is handled by a reusable RestClient layer built using Rest Assured. We reused the RestClient, ConfigurationManager, authentication logic, POJOs and common utilities from our existing 1.1 framework.
>
> ConfigurationManager handles environment and channel-specific configuration, while Jackson and Lombok are used for request and response POJOs. For data-driven testing, we use Cucumber Scenario Outlines with Examples and an Excel utility where larger external datasets are required.
>
> For reporting, we use Allure with the Rest Assured filter to capture request and response details. Cucumber tests are executed through the JUnit runner and can be selectively executed using tags such as smoke and regression."
